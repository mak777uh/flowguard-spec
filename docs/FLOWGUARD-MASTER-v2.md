# FLOWGUARD — мастер-документ v2

**Что это.** Самодостаточный файл для внешнего ревью: продукт, обе ветки, форматы, вердикты, экономика, доктрина цены, реестр утверждений, известные слабости, обязательные измерения, вопросы.
**Что нового в v2.** Первый круг из пяти ревью закрыл часть утверждений и вскрыл три механизма отказа, которых в v1 не было. Ниже всё переписано с учётом этого; в конце — новый набор вопросов.
**Метки:** `[Д]` доказано машинно · `[И]` измерено/воспроизведено · `[Г]` гипотеза.
**Все числа `[Г]` — оценки для планирования, не факты.**

# 1. Ядро

## 1.1. Семь сущностей

**Flow** (защищаемый поток) · **Resource** (адресуемая ценность) · **Subject** (инициатор, только из проверенного источника) · **Policy P** (deny-beats-allow, default deny) · **Closure Z** (все пути изменения ресурса) · **EnforcementPoint M** (единственная точка решения) · **Attestation** (подписанный бандл).

Доменное различие изолируется полем `subject.kind` (`chain.escrow` / `legacy.flow`). Шесть портов: `StateProvider`, `EnforcementPoint`, `ObservationChannel`, `Clock`, `Domain`, `Prover`.

## 1.2. Вердикт — исправлено после ревью

**Три изменения, каждое принципиально:**

**(1) `PROVEN` больше не единственный уровень.** Лестница:

| Уровень | Условие | Для чего годится |
|---|---|---|
| **`PROVEN(R)`** | все конъюнкты `[Д]`; каждое утверждение о полноте опирается на доказанный механизм, а не на тест | наивысшая гарантия |
| **`ENFORCED_TESTED(R)`** | механизм контроля присутствует на **каждом** объявленном денежном пути, но часть свойств проверена тестом `[И]`, а не доказана | честный уровень для legacy-систем, где полнота недоказуема |
| **`INCONCLUSIVE`** | доказательств недостаточно | отчёт без гарантии |
| **`INVALID`** | свидетельство бито | инцидент |

**(2) Вердикт всегда относителен детектору.** Пишется `PROVEN(R)`, где `R` — класс методов обнаружения путей с **измеренным recall** (M1). Формулировка в акте: «обхода нет относительно методов D с recall r на корпусе C», а не «обхода нет».

**(3) Слово `PROVEN` разведено по смыслу.** Ревью показало, что в v1 одно слово означало три разных вещи, включая противоположную («эксплойт воспроизведён» = уязвимость **есть**). Теперь:

| Понятие | Статус |
|---|---|
| Обхода в замыкании нет | `PROVEN(R)` / `ENFORCED_TESTED(R)` — только вердикт `verdict.json` |
| Находка воспроизведена | **`CONFIRMED`** (было `PROVEN`) — `findings/confirmed.json` |
| Находка предположена | **`HYPOTHESIS`** — `findings/hypotheses.json` |

Файлы `confirmed.json` и `hypotheses.json` физически не могут быть смешаны: разные схемы, разные разделы отчёта.

## 1.3. Скаляр покрытия — новое, обязательно

Введено после 5/5 замечания, что `unknown_paths = ∅` доказывает лишь отсутствие неизвестного **внутри модели анализатора**.

```
coverage = covered_paths / discovered_paths
```
Печатается **в заголовке вердикта**, рядом с уровнем:

```
verdict: ENFORCED_TESTED(R2)
coverage: 11/14 (0.79)   excluded: 3   unknown: 0
detector: slither+cast+manual | recall 0.71 (M1, corpus C-20)
```

Правила:
- `PROVEN` требует `coverage = 1.0` **и** `excluded = 0` для денежных путей.
- `ENFORCED_TESTED` требует `coverage ≥ 0.9` и потолок `excluded ≤ 10%` обнаруженных путей.
- `excluded` с `reason` короче заявленного порога и без подтверждающего теста **не принимается**.
- Внешний вызов вне объявленного allowlist → **`INVALID`**, а не `INCONCLUSIVE` (иначе любой контракт с оракулом получает вечный `INCONCLUSIVE`).

## 1.4. Формат `flowguard.yml` — дополнено

```yaml
verdict_requirements:
  min_coverage: 1.0                 # MUST для PROVEN; 0.9 для ENFORCED_TESTED
  max_excluded_ratio: 0.0           # MUST 0 для денежных путей
  detector_recall_min: 0.7          # MUST, из M1 на референсном корпусе
external_calls:
  allowlist: []                      # MUST; вызов вне списка → INVALID
  unknown_behavior: INVALID
token_classes:                       # on-chain
  accepted: [standard_erc20]
  others_behavior: INCONCLUSIVE
```

## 1.5. Бандл — дополнено

Новые обязательные файлы: `verdict.json{level, coverage, detector, recall, excluded}` · `findings/confirmed.json` · `findings/hypotheses.json` · `trust/` (хеши тулчейна, подпись, независимая реплика — §5.5).

## 1.6. Человек в контуре — исправлено

| Контекст | Кто решает |
|---|---|
| Онбординг (SKU 2–3): граница Z, политика P, приёмка доказательства | человек, 4 гейта по 10–30 мин |
| **Рантайм и CI/CD** | **машина, fail-closed**: Z-diff не сходится → деплой блокируется, акт помечается `DEGRADED` |
| Авария | break-glass с HSM-ключом и автосуспензией гарантии |

Ревью верно указало: enterprise не будет читать артефакты формальной верификации на каждый релиз. Ручные гейты — только там, где создаётся гарантия, а не там, где она применяется.

# 2. On-chain: escrow

## 2.1. Три инварианта — с токен-гейтом

| ID | Предикат | Уточнение после ревью |
|---|---|---|
| **INV-1** | `∀a: balanceOf(a) ≥ Σ_{locked,disputed} amount[a]` и `deposited = released + refunded + Σlocked` | **верна только для `standard_erc20`**. Behavioral preflight до прогона: fee-on-transfer, rebasing, pausable, blacklist, upgradeable → **`INCONCLUSIVE`**, если токен нельзя обернуть |
| **INV-2** | `released + refunded ≤ deposited`; переходы монотонны | частичный refund — отдельная модель |
| **INV-3** | `release ⇒ LOCKED ∧ att_VERDICT_OK ∧ subject/recipient/amount match ∧ final(block)` | сравнивать **сумму**, а не только право |

**Новое правило:** изменяемость самого токена (pause/blacklist/upgrade) — это путь вне `Z`. Токен с такими возможностями требует их объявления или даёт `INCONCLUSIVE`.

## 2.2. Пути, финальность, атаки

Семь классов путей (owner/roles · upgrade-proxy · delegatecall · selfdestruct · value-calls · keeper/callback · sweep/rescue); каждый с `gaps[]`. Активный `proxy admin` → `INVALID`.

Финальность: **L1** — `finalized` checkpoint, счётчик блоков как единственный критерий запрещён; **L2** — не одно правило, а **проверяемые адаптеры по сетям** (ревью верно: у каждой L2 своя модель и конфигурация); реорг → `INVALID`.

10 атак A1–A10 — исполняемые скрипты, не агент. Каждая атака обязана **ломать тест на сломанном контракте** (проверка на тавтологичность).

## 2.3. Подписанты

product owner (мультисиг) · custody quorum · security lead · verifier. Для immutable-контракта `custody quorum` заменяется на «подтверждение отсутствия привилегий» с доказательством через отсутствие ролей в storage.

# 3. Legacy: сервис с БД

## 3.1. Замыкание Z — 13 элементов

Двенадцать из v1 плюс тринадцатый по ревью: **исходящие интеграции и общие секреты** (сторонний SaaS с общим кредом, теневые интеграции). Он не был назван, потому что все смотрели внутрь периметра.

## 3.2. Семь путей обхода

Без изменений: batch · админка · restore (только через подписанный снапшот + 6 шагов) · партнёрский API · прямой доступ к БД (запретить) · логи/аналитика (запретить запись) · CI/supply chain (запретить креды данных).

## 3.3. Триггер — переписан после ревью

**Слово «физическая гарантия» снято.** Триггер — часть изменяемой конфигурации СУБД, а не независимая граница против администратора.

Что теперь обязательно:

| Требование | Почему |
|---|---|
| Триггеры на **весь DML** (`INSERT/UPDATE/DELETE/TRUNCATE`), не только `UPDATE` | v1 покрывал только `UPDATE` — ревью право |
| **DDL event trigger** на `ALTER/DROP TRIGGER`, `ALTER TABLE` | иначе триггер отключается одной командой |
| **Хеш дельты в `Permit`**: не только «право», но и **что именно меняется** (старое → новое) | иначе `Permit` на право без суммы, ревью право |
| **Мониторинг суперпользовательских сессий** как отдельный канал witness | `rds_superuser`/`postgres` может всё |
| **Запрет logical replication** на денежных таблицах | replication применяет изменения мимо триггеров |
| `session_replication_role` под контролем, изменение = инцидент | классический обход триггеров |

**Условие заявления гарантии:** гарантия уровня `ENFORCED_TESTED` допустима только при **явно объявленной модели привилегий**, где администратор БД исключён из модели нарушителя. Если админ в модели нарушителя — уровень не выше `INCONCLUSIVE`, и это пишется в акте.

## 3.4. `Allow`-событие — привязано криптографически

Было: «сверка `pgaudit` с журналом `Allow`». Ревью 4/5 верно указало, что обходной писатель напишет и `Allow`.

Стало: `Allow`-событие обязано содержать `permit.nonce`, `permit.resource_version` и `permit.signature`, а сверка — проверять **криптографическую связку** «событие ↔ `Permit` ↔ мутация» в одной транзакции. Наличие события без валидной подписи — `INVALID`, не «подтверждение».

## 3.5. Witness — плюс два требования

Три канала (tap, DB-дайджест, идентичность) · 12 человеко-дней `[Г]` · два теста (A — целостность, B — независимость).

Добавлено по ревью:
- **тест на подмену цели**: заменить код/сборку/конфиг/идентичность цели и проверить, что сквозная связка target → артефакты → digest → подписи → offline verify это ловит (это механизм `T1`);
- **независимость каналов проверяется по отдельности**: журнал не считается независимым, если пишется тем же процессом, что и мутация.

## 3.6. Оракулы — усилено

Три класса (SQLi, BOLA, traversal). `CONFIRMED` требует `C=false ∧ T=true ∧ N=false`.

Изменено после 4/5 замечаний:
- **K ≥ 5** по умолчанию; **K = 10** при неизвестном flake rate;
- **любое расхождение** между прогонами → эскалация до 10 → при сохранении расхождения `INCONCLUSIVE`;
- **публикуемая верхняя граница FP** по каждому оракулу, измеренная на негативном корпусе;
- отдельный режим `nondeterministic_oracle`: не претендует на `CONFIRMED`, только `HYPOTHESIS` с гистограммой.

## 3.7. Прочее без изменений

7 атак · 8 инвариантов (I1, I6, I8 — `[И]`, не `[Д]`) · два раздельных утверждения (`∀ Permit ⟹ P` и `∀ мутация ⟹ ∃ Permit ∧ Allow`) · акт из 8 полей с 4 подписями, две у клиента · правило 3 дней + `DEGRADED` · break-glass через HSM · контракт валидируемости.

# 4. Экономика и цена

## 4.1. SKU — с учётом ревью

| # | SKU | Цена | Срок | Ключевая правка |
|---|---|---|---|---|
| 1 | Базовый анализ | $2–5k | 3–5 дн | **pass-through себестоимости ревью** до закрытия M2; не обещать маржу >80% |
| 2 | Патчи | $5–10k | 2 нед | — |
| 3 | Миграция | $25–45k | 4–6 нед | — |
| 4 | Гарантия | `clamp(v×k, $25k, $50k)` для v1 | 45 дн | **потолок снижен до $50k**; пол поднят до $25k (пол $12k был ниже себестоимости witness) |
| 5 | Ре-аттестация | в подписке | 15 мин | — |

**Правило цены после ревью:** предложение обязано содержать **доверительный интервал на `v`**. Если разброс >3× — либо отказ от гарантии (только анализ), либо пересчёт после уточнения `v`. Публиковать прайс до накопления актуарного трек-рода нельзя.

`k`: 0.60% до $10M · 0.30% до $100M · 0.15% выше. `value_at_risk` — суточный неотмитигированный поток, не капитализация. После M7 пересчитать: при witness 30 ч-дней SKU-4 убыточен до `v ≈ $5–7M`.

## 4.2. Доктрина цены — без изменений по существу, с поправкой на ревью

P1–P6 в силе (не цена за находку · потолок маржи 45/70% · дивиденд автоматизации 50/50 · цена падает по расписанию · нет премии за страх · критическая инфраструктура по себестоимости).

**Поправка:** `assessor_minutes_per_finding` — планировочное значение **35–40 минут** (консенсус пяти ревью: 20, 25, 35, 45, 45), а 15 минут — цель, достижимая не раньше второго квартала инструмента. Условное обязательство по цене (снижение 10%/год) остаётся, но отсчитывается **от измеренного значения**, а не от целевого.

Дивиденд автоматизации в числах пересчитан: при 40 → 15 мин экономия на ангажементе ≈ `(0.67 − 0.25) × 120 × 4 = $200` `[Г]` — то есть пока дивиденд мал, и это надо признать, а не обещать.

# 9. Что от тебя нужно (круг 2)

Первый круг дал главное: **все пять ревью оценили медиану находок в ≈1**, то есть по собственному критерию смерти legacy в текущем виде строить нельзя. Второй круг должен решить, **что именно меняем**, а не перепроверить то же.

**A. Что менять в продукте.** По трём вариантам ответа на провал критерия `G25`:
 (а) сузить scope до изолированного леджера-ядра, остальное — вне гарантии;
 (б) сменить метрику: не урожай находок, а доля целей с `closure_complete`;
 (в) принять, что гарантия продаётся и при нуле находок, и убрать `G25` совсем.
Выбери один, обоснуй в 3 строках и укажи, что он ломает.

**B. Три доказательства, без которых гарантию продавать нельзя** (по итогам круга 1: полнота замыкания, независимость свидетельства, отсутствие ложного `PROVEN`). Для каждого: **один** дешёвый эксперимент (≤5 дней) с порогом провала.

**C. `T3` — вакуумный PROVEN.** Дай три ограничения, которые не дают клиенту сузить `Z`/ослабить `P` и при этом не делают продукт непродаваемым. Числа, если можешь.

**D. `T1` — доверенный контур.** Что должно быть в бандле, чтобы проверяющий мог убедиться в связи «цель ↔ артефакт ↔ вердикт», не доверяя нам? Перечисли поля и один тест подмены.

**E. Одно «не строить».** Одно наблюдаемое условие, при котором продукт в этом виде не надо строить. Не повторяй условие из §7.M8 — дай своё.

**F. Одно число.** `assessor_minutes_per_finding` — твоя оценка и способ проверки. Если считаешь, что 15 минут недостижимы в принципе — скажи это прямо.

**Правила:** ≤200 слов на пункт · запрещено «зависит от контекста» без условия · «не знаю» разрешено и ценится · не предлагай новых архитектур, только правки · не пересказывай документ.
