# 01. Варианты архитектуры: не три проекта, а матрица

> Главный вывод первого круга: «облако vs on-prem» — это **не вариант архитектуры**, а ось размещения. Девять источников казались несовместимыми потому, что стояли в разных точках одной матрицы. Ниже — матрица и три именованных продукта в ней.

---

## 1. Три оси

```
ОСЬ 1 — УРОВЕНЬ ГАРАНТИЙ (что продаём)
  V1 offense-gated      → «доказанный баг + доказанный фикс»
  V2 remediation factory→ «лестница исправлений с паспортом доказательств»
  V3 certified change   → «минимальное сертифицируемое изменение + пакет для органа»

ОСЬ 2 — РАЗМЕЩЕНИЕ (где исполняется)
  D1 SaaS               → всё у нас; быстрее всех, доверие кодом не куплено
  D2 hybrid runner      → панель у нас, код и инструменты в VPC клиента   ← дефолт
  D3 on-prem / air-gap  → ничего не выходит; продаётся лицензией

ОСЬ 3 — ОХВАТ (что на входе)
  S1 repo / archive / SBOM / image
  S2 + API-spec / IaC
  S3 + live targets (подписанный scope)
  S4 + формальное ядро (spec + proofs)
```

Продуктовая линейка = три именованных пакета, каждый доступен в трёх размещениях:

| | V1 «Доказанный баг» | V2 «Фабрика ремедиации» | V3 «Сертифицируемое изменение» |
|---|---|---|---|
| Ось 1 | offense-gated | offense-gated + grid + evidence | + детерминированный evidence engine в TCB |
| Ось 3 | S1–S2 | S1–S3 | S1–S4 |
| Ось 2 | D1, D2 | D1, D2, D3 | D2, D3 (D3 обязателен) |
| Срок до первого клиента | 8–10 недель | 4–6 месяцев | 9–15 месяцев |
| Чек | €8–15k | €15–60k + ретейнер | €150–500k, годовой контракт |
| Маржа | высокая | средняя → высокая при каталогизации | низкая в v1, IRR на 3-м клиенте |

## 2. V1 — «Доказанный баг» (первый релиз)

**Ставка:** продаём не отчёт, а **бандл**, который клиент переигрывает у себя за 4 минуты и получает тот же результат.

```
 intake ──► scope manifest (подписан) ──► run compiler
                                              │
                          ┌───────────────────┴───────────────────┐
                          ▼                                       ▼
                 Lane A: coverage                        Lane B: proof
                 SAST / SCA / secrets / IaC              агент дожимает кандидата
                 → HYPOTHESIS (не биллится)              → C/T/N × K (3 → 10)
                          │                                       │
                          └───────────────┬───────────────────────┘
                                          ▼
                            evidence plane (content-addressed)
                            manifest · hash-chain · replay kit
                                          │
                                          ▼
                            named assessor SIGNS → отчёт
```

**Что доказывает:** «существует вход, при котором наблюдается эффект X, и он исчезает после патча Y на коммите Z».
**Что НЕ доказывает:** отсутствие других уязвимостей, отсутствие поломок вне тестов, безопасность системы. Никогда не формулировать иначе.

**Минимальный состав (обязательное ядро, всё остальное режется):**

| Компонент | Минимум для V1 | Почему нельзя вырезать |
|---|---|---|
| Sandbox | Firecracker microVM (Tier A — недоверенный код цели), gVisor runsc (Tier B — свои инструменты), per-run, deny-all egress. **Bare-metal узлы: вложенной виртуализации избегаем**, иначе теряется смысл микроVM | без него нет ни PoC, ни юридической защиты. Цена решения — bare-metal дороже облака, это прямая поправка к unit-экономике (см. `03-EVAL-ROADMAP.md` §5) |
| PoC-контракт | ⟨F,A,T,O,V,S⟩ + C/T/N × **K адаптивный**: 3 по умолчанию, эскалация до 10 только при неоднозначности; K печатается в бандле | это и есть продукт; без него — ещё один сканер. Фиксированный K=10 × 3 ветки × N перезапусков stateful-цели — главный источник взрыва стоимости (оценка рецензента №1) |
| Prefetch зависимостей | allowlist-зеркало реестров, прогрев **до** запечатывания | deny-all по умолчанию ломает сборку: зависимости тянутся из сети, `DEPLOY_FAILED` даёт ноль находок |
| Запечатанный оракул | шаблоны на стек, агент не пишет предикат | единственный барьер против «я решил, что это баг» |
| Canary-nonce | на каждый прогон, в canary-store вне VM | делает хардкод PoC физически невозможным |
| Evidence plane | sha256 + манифест + replay kit офлайн | без него нет подписи, а без подписи нет цены |
| Named signatory | человек, 100% PROVEN перед отгрузкой | это то, что покупают |
| Негативный скоуп | обязательный раздел | без него отчёт не ограничивает утверждение |

**Режимы отказа, которые V1 допускает осознанно:** систематические ложные негативы (длинные бизнес-цепочки, мульти-тенант, требования к данным); гонки и DoS — только статистически; `DEPLOY_FAILED` на монолитах с неясным деплоем.

**Когда V1 оптимален:** есть разворачиваемый инстанс; у клиента FP-усталость; нужен артефакт для аудита/страховки/спора с подрядчиком; C/C++ с приоритизацией по эксплуатируемости.

## 3. V2 — «Фабрика ремедиации» (рекомендуемое ядро)

**Ставка:** находка — это вход, а продукт — **сравнение вариантов исправления с паспортами доказательств**. V1 внутри, плюс четыре новых подсистемы.

```
                              ┌──────────────────────────┐
   V1 (offense-gated) ───────►│  ROOT-CAUSE GRAPH        │
                              │  asset·threat·finding·   │
                              │  cause·invariant·fix·    │
                              │  artifact·verification·  │
                              │  residual-risk·decision  │
                              └───────────┬──────────────┘
                                          ▼
                    ┌─────────────────────┴─────────────────────┐
                    ▼                     ▼                     ▼
              R0–R2 (дёшево)        R3 (рефакторинг)      R4–R5 (ядро)
              hotfix / патч         класс, не инстанс     memory-safe / proof
                    └─────────────────────┬─────────────────────┘
                                          ▼
                            VERIFIER FARM (вне write-scope агента)
                            PoC-гашение · variant suite · регрессия ·
                            diff-fuzz · perf-бюджет · proof-check
                                          │
                                          ▼
                            ФРОНТ ПАРЕТО (не «лучший фикс»)
                            + паспорт каждого варианта
                                          │
                                          ▼
                            решение клиента → PR / план миграции
```

**Четыре подсистемы, которых нет в V1:**

1. **Root-cause graph.** Типизированные узлы и связи (`caused_by`, `violates`, `mitigates`, `verified_by`, `introduces_risk`), каждая связь с провенансом: код / результат инструмента / явная гипотеза. Отвечает на вопросы, на которые сканер не отвечает: какие фиксы закрывают несколько находок; что останется после минимального патча; какие доказательства протухнут при изменении файла.
2. **Peer-генерация вариантов.** R0–R5 генерируются разными моделями/сидами в изолированных ветках, не видящих друг друга (защита от коррелированной ошибки). Конфликт — не текстовый merge, а содержательный конфликт для отчёта.
3. **Verifier farm.** Всё, что проверяет, лежит в read-only, вне write-scope агента; попытка записи в `tests/`, `spec/`, CI — инцидент, а не мелочь. Агент может править только `src/` и только в своей ветке.
4. **Фронт Парето вместо рейтинга.** Никаких «безопасность 97/100». Каждый вариант — вектор: закрывает / ломает / доказуемо / стоит / откатывается / остаточный риск.

**Экономика V2 (модель, не факт):** R0–R1 — товар с высокой маржой и вход в аккаунт; R2 — лучший ROI; R3 — главный дифференциатор; R4–R5 — штучный премиум. Каталогизация R0–R2 в упакованные «паки» — единственный способ не сползти в консалтинговую маржу.

**Когда V2 оптимален:** продуктовые команды с CI; клиенты, у которых уже есть сканеры и болит не «найти», а «закрыть и доказать»; любой сегмент с аудитом.

## 4. V3 — «Сертифицируемое изменение» (ров и второй продукт)

**Ставка:** в регулируемом домене агент **не может** быть автором доказательства. Он — поисковая эвристика над формально определённой функцией цели. Единственный писатель в хранилище доказательств — детерминированный арбитр.

```
КЛИЕНТ: VPC / on-prem / air-gap, источник не покидает контур
   │
[1] INTAKE ── базовая линия: SCI, manifest, scope letter,
    класс (DAL / ASIL / класс IEC 62304 / SIL / PCI-скоуп), certification basis
   │
[2] EVIDENCE ENGINE ← детерминированный, ВХОДИТ В TCB
    reproducible build · coding standards (MISRA/CERT-C) · анализаторы ·
    покрытие (включая независимость MC/DC-пар) · фаззеры+санитайзеры ·
    SBOM · index конфигурации
    → подписанные неизменяемые evidence records = ФАКТЫ
   │
[3] AGENT LAYER ← ВНЕ TCB, read-only на источник, запись только в scratch
    гипотезы: где искать доказательство, какой PO разрядить
   │
[4] ARBITER ← детерминированный, единственный писатель
    проверяет PO, строит пакет, считает покрытие и остаточный риск
   │
[5] HUMAN SIGN-OFF ── сертификационный инженер / DER-liaison
   │
[6] CERTIFICATION PACKAGE: трассируемость · PO-реестр · assumptions ledger ·
    TCB · «на что не смотрели» · impact analysis
```

**Единица работы — не уязвимость, а сертификационное ожидание (objective).** CWE — метаданные. Если находка не отображается в цель стандарта, она нерелевантна, сколько бы истинной ни была.

**Почему «просто патч» здесь часто запрещён:** изменение кода — регрессия сертификационного базиса; даже семантически нейтральная правка обесценивает ранее собранные доказательства для затронутого блока. Поэтому продаётся **минимальное сертифицируемое изменение** с предвычисленной ценой, включая честный вариант «принять риск с компенсирующим контролем и подписью» как отдельную оплачиваемую позицию.

**Экономика:** в v1 — 19% GM и полугодовой кэш-цикл. Это не продукт, а **кредибилити-актив**. Продуктом становится при выполнении критерия: второй клиент на том же классе свойств с переиспользованием proof-харнесса ≥ 70%.

**Когда V3 оптимален:** авионика, автопром, медицина, промышленность, платежи; клиент уже покупает верификацию (бюджетная строка не дискреционна); горизонт — годы.

## 5. Почему не наоборот: порядок ставок

| Порядок | Что строим | Почему именно так |
|---|---|---|
| 1 | V1 + подпись + evidence | даёт цену и доверие за 10 недель; без этого V2 нечего продавать |
| 2 | V2 (graph, grid, verifier farm) | превращает разовую находку в подписку; создаёт фронт Парето |
| 3 | V3 на одном классе свойств | единственный способ получить ров; но требует денег от V2 |
| параллельно | ось D2 → D3 | гибридный runner с первого дня, иначе enterprise-сделки недоступны |
| опция | evidence-plane как сервис | страховка от коммодитизации агентов; стоит 0 сейчас, если API спроектирован сразу |

Обратный порядок (сразу V3, или сразу «платформа для чужих агентов») — типичная ошибка: нет ни доверия, ни данных, ни денег на доказательства.

---

## 6. Чего не делает ни один вариант

- Не гарантирует отсутствие уязвимостей — и не должен формулировать отчёт так, чтобы это читалось.
- Не деплоит в прод и не мержит PR.
- Не тестирует системы, которыми клиент не владеет.
- Не сертифицирует соответствие — поставляет доказательства, не сертификаты.
- Не обещает «доказанную constant-time»: функциональная верификация побочные каналы не покрывает.
- Не публикует «security score» как основной деливерабл.
